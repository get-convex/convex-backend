The `db.vars.commitTs` symbol can be used to implement efficient iteration over
a table. Some potential use cases include modeling a FIFO queue (e.g. with the
[batch worker component](https://github.com/get-convex/batch-worker)), or for an
`updatedAt` field, which allows you to continually iterate over new updates in a
table without needing to delete or insert entries.

<Snippet source={commitTsExample} snippet="insert" title="convex/work.ts" />

`db.vars.commitTs` is a placeholder value while the mutation executes. When the
mutation commits, the value gets resolved to the commit timestamp in
nanoseconds.

## Commit timestamp vs. `_creationTime`

Note that the commit timestamp is not the same as the `_creationTime` system
field. The commit timestamp is strictly increasing, so the resolved
`db.vars.commitTs` values for different documents are guaranteed to be ordered
the same way as the corresponding mutations that committed the documents (note
that documents updated in the same transaction will all have the same commit
timestamp).

On the other hand, `_creationTime` does not have this same guarantee, as it is
set when the mutation begins executing. Since mutations execute concurrently
before committing, `_creationTime` does not reflect the order in which the
mutations are committed. Furthermore, unlike `db.vars.commitTs`, `_creationTime`
is in milliseconds.

Iterating over a table using the commit timestamp is more efficient because it
enables skipping over tombstones. When you delete a document, Convex writes a
tombstone in the place of the document that indicates it was deleted. However,
tombstones still take up space in indexes. If you are using `_creationTime` as a
cursor, new documents may be inserted with an earlier `_creationTime` after you
have already deleted documents with later `_creationTime`. Scanning through the
`_creationTime` index may iterate over many tombstones, especially if you have a
delete-heavy workload on your table.

With an index on `db.vars.commitTs`, you do not need to worry about this, as the
timestamp is strictly increasing. Since inserted documents will always have a
greater commit timestamp, the tombstones will always end where the new documents
begin.

## Using the commit timestamp

During function execution, new documents inserted with `db.vars.commitTs` will
have the `CommitTsPlaceholder`. Resolved commit timestamps are Int64s. You can
use the `v.commitTs()` validator in argument and return validators and schema
definitions. It accepts both placeholders and the resolved Int64 values for the
commit timestamp.
